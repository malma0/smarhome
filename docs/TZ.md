## 1. Суть продукта

Строим премиальные квартиры/дома под ключ (старт — Новосибирск, дальше Россия, потом мир). На этапе стройки в дом закладывается полный стек умного дома — не только климат и датчики, а вообще всё, что можно автоматизировать: свет, шторы, замки, сигнализация, медиа, бытовая техника, энергетика, участок. Скрытые микрофоны и динамики встроены в потолок/стены, без видимых колонок.

Внутри дома живёт **Jarvis** — ИИ-ассистент:
- с ним можно говорить голосом в любой комнате;
- он управляет буквально всем в доме, что подключено к системе;
- у жильцов есть iPad mini, вмонтированный в стену как пульт — тот же Jarvis, но с экраном.

## 2. Зачем и почему

- **Зачем**: дифференциатор премиум-сегмента жилья. Не «умный дом как набор гаджетов», а цельный ИИ-дворецкий, встроенный в архитектуру дома с самого начала стройки — это нельзя докупить постфактум как колонку с Алисой.
- **Бизнес-модель на старте**: разовые премиум-проекты (стройка + интеграция), не подписка. Экономика — через маржу на самих объектах, не на SaaS.
- **Почему не с нуля**:
  - Голосовое железо — OEM/white-label модули под своим брендом, не разработка чипов/акустики с нуля.
  - Управление устройствами — через Home Assistant, а не собственный протокол опроса датчиков/кондиционеров/замков/медиаплееров.
  - Голосовой пайплайн — поверх готовой agent-платформы (LiveKit Agents / Vapi / Retell), не свой STT/оркестратор.
  - Логика в этих местах — не наше УТП. Наше УТП — то, как это всё интегрировано в стройку и как ведёт себя ассистент.

## 3. Кто пользователь

- **Жилец** — говорит с Jarvis голосом или через iPad-панель. У Jarvis есть характер (см. раздел 5), который либо выбирается жильцом, либо подстраивается под него сам.
- **Семья в целом** — предпочтения хранятся на уровне и семьи, и отдельных её членов (не только «последняя команда»).
- **Мы (на этапе стройки)** — закладываем железо и разворачиваем backend как часть сдачи объекта.

## 4. Архитектура

Ключевая идея: **ядро ИИ ничего не знает о конкретных устройствах и не завязано на конкретную LLM**. Оно гоняет цикл tool use (через свой `LLMProvider`-адаптер) над реестром тулов, которые ему подставляют снаружи — сегодня в реестре может быть один тул на домен `light`, завтра туда же добавляется `lock`, и ядро не меняется ни строчкой; так же и смена LLM-провайдера не должна требовать переписывания ядра.

```
Жилец (голос / iPad)                                    <- фаза 7-8, пока не реализовано
        │
        ▼
Voice-agent платформа (LiveKit Agents / Vapi / Retell)   <- фаза 7, пока не реализовано
   STT → [ Jarvis backend ] → TTS (ElevenLabs, офлайн-фолбэк Piper)
        │
        ▼
┌─────────────────────────────────────────────────────────────┐
│ Jarvis backend                                                │
│                                                                 │
│  Ядро ИИ (device-agnostic И llm-agnostic, фаза 0)               │
│   ├── цикл tool use через LLMProvider-адаптер (Claude — дефолт) │
│   ├── характер/персона (butler / warm / adaptive-обучаемая)     │
│   └── память: предпочтения по устройствам + стиль общения      │
│         по каждому resident_id                                 │
│                                                                 │
│  Реестр доменных тулов (фаза 1+, растёт по одному домену)      │
│   ├── control_light, control_switch      (фаза 1)              │
│   ├── control_cover                       (фаза 2)              │
│   ├── control_climate, control_humidifier (фаза 3)              │
│   ├── control_media_player, control_vacuum(фаза 4)              │
│   ├── control_energy, control_valve, ...  (фаза 5)              │
│   └── control_lock, arm_alarm, ...        (фаза 6, максимум     │
│       safety — по умолчанию только чтение статуса)              │
│                                                                 │
│  Слой внимания — rule-engine на порогах (не LLM)     <- позже   │
└─────────────────────────────────────────────────────────────┘
        │
        ▼
Home Assistant → реальные/mock-устройства по всем доменам дома
```

Jarvis **не** получает непрерывный поток сырых показаний датчиков. Он либо сам запрашивает снимок состояния через tool use, либо (в будущем) его будит слой внимания, когда порог нарушен.

### Карта доменов умного дома

| Категория | Примеры | Домен HA | Фаза |
|---|---|---|---|
| Свет/розетки | сцены, диммер, цветовая температура, обычные розетки | `light`, `switch`, `scene` | 1 |
| Окна/проёмы | шторы, жалюзи, ставни, гаражные ворота, ворота участка | `cover` | 2 |
| Климат и воздух | температура, увлажнитель/осушитель, очистка воздуха, тёплый пол | `climate`, `humidifier`, `fan` | 3 |
| Медиа и техника | ТВ, многозонный звук, робот-пылесос, водонагреватель | `media_player`, `vacuum`, `water_heater` | 4 |
| Энергетика/вода/участок | счётчики, солнечные панели, зарядка EV, полив, протечки, бассейн | `sensor`, `valve`, `switch` | 5 |
| Безопасность и доступ | замки, сигнализация, камеры, видеодомофон | `lock`, `alarm_control_panel`, `camera`, `binary_sensor` | 6 (максимум safety) |
| Присутствие/контекст | геолокация жильцов, датчики занятости, календарь | `device_tracker`, `binary_sensor`, `calendar` | не назначена |

Порядок фаз 1→6 — от простого/безопасного к сложному/рискованному: `light`/`switch` — банальный on/off без диапазонов, `lock`/`alarm_control_panel`/`camera` — самый высокий риск, поэтому в конце и с самой жёсткой safety-политикой.

## 5. Персонализация: характер и память

Это часть ядра ИИ (фаза 0), не умного дома — работает даже без единого подключённого устройства.

- **Три режима характера**, выбираются жильцом (переключаемо в любой момент):
  1. **Сдержанный дворецкий** — статусная, ироничная подача, как у Старка.
  2. **Тёплый семейный помощник** — заботливая, менее формальная подача, лучше заходит с детьми.
  3. **Адаптивный** — начинает нейтрально, затем подстраивается под темперамент и манеру речи конкретного жильца (примерно за неделю использования должен «понимать», как с ним общаться). Это не просто выбор пресета — отдельный обучаемый на реальных диалогах компонент (детали проектируются в фазе 0), а не только промпт-инжиниринг поверх LLM.
- **Память** хранит не только предпочтения по устройствам («Иван любит 21°C в кабинете вечером»), но и стиль общения для адаптивного режима (формальность, многословность, юмор) — по каждому члену семьи отдельно.
- **Идентификация говорящего**: пока нет голосового пайплайна с распознаванием говорящего, backend принимает явный `resident_id` рядом с `session_id` — заглушка, которую голосовой слой позже заполнит реальным результатом speaker ID без изменений в остальной логике.
- **Проактивность слоя внимания настраивается жильцом**, а не зашита константой: уровень (например, тихий/сбалансированный/разговорчивый — конкретные градации проектируются вместе со слоем внимания) хранится в том же settings-хранилище, что и характер, на уровне дома. До появления iPad-приложения (фаза 8) значение меняется напрямую через backend-настройки; в приложении это просто UI поверх того же поля. MVP слоя внимания стартует с консервативного значения по умолчанию (только безопасность/критичное), чтобы не быть навязчивым, пока жилец явно не увеличил уровень.

## 6. Принятые технические решения (не пересматривать без явной причины)

| Решение | Что | Почему |
|---|---|---|
| Язык backend | Python | HA написан на Python — вся экосистема интеграций под него; Anthropic SDK и LiveKit Agents (голосовой слой) тоже Python-first |
| Слой устройств | Home Assistant | готовые интеграции для тысяч устройств любого домена — не пишем свой протокол ни для датчиков, ни для замков, ни для медиаплееров |
| Мозг Jarvis | LLM за своим адаптером (`LLMProvider`), не прямой вызов SDK по коду; провайдер по умолчанию — Claude API, tool use | ядро device-agnostic И llm-agnostic; финальный выбор модели — открытый пункт (см. раздел 9), смена не должна требовать переписывания ядра |
| Общие вопросы (не про дом) | Jarvis отвечает как полноценный ассистент (как Алиса/Алекса) — общие знания модели + погода через HA `weather` | пользователь явно попросил не ограничивать Jarvis только командами дому; живые внешние данные (новости/курсы/спорт) вне HA — открытый пункт, см. раздел 9 |
| Safety-политика | per-domain, в коде дispatch-а, не только в промпте | у `light` и `lock` принципиально разный уровень риска — единая политика на все домены не годится |
| Голос (позже) | LiveKit Agents / Vapi / Retell + ElevenLabs (TTS), Piper (офлайн-фолбэк) | не собираем голосовой пайплайн с нуля |
| iPad-приложение (позже) | Apple Business Manager (Custom Apps) + MDM Kiosk Mode | **не** Apple Developer Enterprise Program — против правил Apple для внешних клиентов, риск массового отзыва сертификата |
| Память | персистентное хранилище (SQLite для старта), часть ядра ИИ (фаза 0), не умного дома | нужна уже для характера/персонализации, а не только для предпочтений по устройствам |

## 7. Правила безопасности (жёстко в коде, не только в промпте)

Общие для всех доменов:
1. Любое физическое действие идёт через generic-тул своего домена, к которому привязана своя safety-политика — единого «пропусти всё» тула нет.
2. Резкие изменения в нескольких комнатах/объектах за один ход диалога → короткое подтверждение у жильца, прежде чем трогать второй.

Специфичные для доменов, уже реализованных или спроектированных:
- **Климат**: нельзя менять температуру за пределы **16–28°C** без явного подтверждения жильца; за пределами **5–35°C** — отказ безусловно, даже с подтверждением.
- **Вентиляция**: нет инструмента управления процентом кислорода — это стабильный параметр атмосферы, не ручка. Жалобы на духоту → `boost_ventilation`/`control_fan`, и только так.
- **Безопасность/доступ** (фаза 6, ещё не реализовано, принцип зафиксирован заранее): по умолчанию Jarvis только читает статус замков/сигнализации/датчиков. Открыть замок или снять с охраны — всегда явное подтверждение, без исключений и без права «запомнить и не спрашивать в следующий раз».
- **Камеры**: Jarvis не получает видео/фото с камер вообще — только события от датчиков движения («обнаружено движение»). Это решение по приватности, не техническое ограничение.
- **Микрофоны**: аудио передаётся дальше локального wake-word движка OEM-модуля только после произнесённого имени — до этого момента ничего не стримится и не анализируется облаком. Слой внимания работает исключительно по телеметрии Home Assistant (датчики), а не по аудио — то есть проактивность **никогда** не требует фонового прослушивания разговоров.

## 9. Решённые и открытые вопросы

Большинство вопросов, поднятых при подготовке v0.2, закрыты — либо решением, либо осознанной отсрочкой с понятным триггером. Остался один по-настоящему открытый пункт (ниже отдельно) — это нормально, не всё нужно решать раньше, чем появится реальная причина.

| Вопрос | Решение |
|---|---|
| Приватность и всегда-слушающие микрофоны | Закрыто. Аудио идёт дальше локального wake-word движка только после имени; слой внимания работает по телеметрии HA, не по аудио. См. раздел 7. |
| Степень проактивности слоя внимания | Закрыто. Настраивается жильцом (settings-хранилище), MVP стартует с консервативного значения по умолчанию. См. раздел 5. |
| Формат хранилища памяти | Закрыто. Плоский SQLite на весь диапазон фаз 0–6; пересматривается только если реально упрёмся в масштаб (не ожидается для одного дома). |
| Нужен ли Jarvis веб-поиск для live-данных (новости/курсы/спорт) вне HA | Закрыто: да. Реализуем как свой тул поверх стороннего поискового API — не встроенная функция конкретного LLM-провайдера, чтобы не зависеть от выбора модели. Погода закрывается отдельно, через штатный домен HA `weather`. |
| Выбор voice-agent платформы (LiveKit Agents / Vapi / Retell) | Осознанно отложено. Backend — чёрный ящик для любой из них, выбор не влияет на фазы 0–6. Сравнение по цене/латентности делаем перед стартом фазы 7, не раньше. |
| OTA-стратегия для OEM voice-модулей и iPad | Осознанно отложено. Зависит от выбора OEM-вендора голосового железа, которого ещё нет. Решается вместе с этим выбором, вне backend-разработки. |

### Открытый вопрос: какая LLM в итоге под капотом

Изначально в брифе — Claude API без вариантов. Причина пересмотра: продукт должен продаваться, но параллельно служит портфолио под трудоустройство в разработку ИИ — а конкурентоспособную модель с нуля в одиночку не поднять, так что ценность портфолио должна идти не из "своей LLM", а из архитектуры вокруг неё.

Решено пока: ядро строится **llm-agnostic** (адаптер `LLMProvider`, ядро не завязано на конкретный SDK), провайдер по умолчанию на время разработки фаз 0–1 — Claude API (уже протестирован в прототипе). Финальный выбор модели для продукта — открыт, решается при появлении конкретной причины (стоимость, доступ/оплата из РФ, требования конкретного клиента, зрелость open-source альтернативы под tool use). Смена провайдера не должна требовать переписывания ядра — это и есть проверка того, что адаптер сделан правильно.

Отдельно от выбора модели: **адаптивная персона** (раздел 5, пункт 3) — вот тот компонент, который проектируется и обучается нами, независимо от того, какая LLM в итоге выбрана под капотом основного диалога. Это и есть "свой ИИ" для портфолио, спроектированный так, что он не выбрасывается при смене провайдера.
