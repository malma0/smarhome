# Jarvis — техническое задание (v0.1)

## 1. Суть продукта

Строим премиальные квартиры/дома под ключ (старт — Новосибирск, дальше Россия, потом мир). На этапе стройки в дом закладывается полный стек умного дома: климат-контроль, датчики (температура, влажность, CO2), скрытые микрофоны и динамики (встроены в потолок/стены, без видимых колонок).

Внутри дома живёт **Jarvis** — ИИ-ассистент:
- с ним можно говорить голосом в любой комнате;
- он управляет домом (климат, свет, вентиляция);
- у жильцов есть iPad mini, вмонтированный в стену как пульт — тот же Jarvis, но с экраном.

## 2. Зачем и почему

- **Зачем**: дифференциатор премиум-сегмента жилья. Не «умный дом как набор гаджетов», а цельный ИИ-дворецкий, встроенный в архитектуру дома с самого начала стройки — это нельзя докупить постфактум как колонку с Алисой.
- **Бизнес-модель на старте**: разовые премиум-проекты (стройка + интеграция), не подписка. Экономика — через маржу на самих объектах, не на SaaS.
- **Почему не с нуля**:
  - Голосовое железо — OEM/white-label модули под своим брендом, не разработка чипов/акустики с нуля.
  - Управление устройствами — через Home Assistant, а не собственный протокол опроса датчиков/кондиционеров.
  - Голосовой пайплайн — поверх готовой agent-платформы (LiveKit Agents / Vapi / Retell), не свой STT/оркестратор.
  - Логика в этих местах — не наше УТП. Наше УТП — то, как это всё интегрировано в стройку и как ведёт себя ассистент.

## 3. Кто пользователь

- **Жилец** — говорит с Jarvis голосом или через iPad-панель, получает управление климатом/светом/вентиляцией и естественный диалог.
- **Семья в целом** — у Jarvis есть память предпочтений на уровне семьи/членов семьи (не только «последняя команда»).
- **Мы (на этапе стройки)** — закладываем железо и разворачиваем backend как часть сдачи объекта.

## 4. Архитектура

```
Жилец (голос / iPad)
        │
        ▼
Voice-agent платформа (LiveKit Agents / Vapi / Retell)
   STT → [ Jarvis backend ] → TTS (ElevenLabs, офлайн-фолбэк Piper)
        │
        ▼
Jarvis backend (Claude API, tool use)
   ├── Слой данных     — Home Assistant (состояние + история)
   ├── Слой контекста  — компактный снимок дома по запросу (tool use)
   ├── Слой внимания   — rule-engine на порогах (не LLM), инициирует проактивные реплики
   └── Слой памяти     — предпочтения семьи, отдельное персистентное хранилище
        │
        ▼
Home Assistant → реальные/mock-устройства по комнатам
```

Ключевой принцип: Jarvis **не** получает непрерывный поток сырых показаний датчиков. Он либо сам запрашивает снимок состояния через tool use, либо его будит слой внимания, когда порог нарушен (например, CO2 > 1200 ppm дольше 10 минут).

## 5. Принятые технические решения (не пересматривать без явной причины)

| Решение | Что | Почему |
|---|---|---|
| Язык backend | Python | HA написан на Python — вся экосистема интеграций под него; Anthropic SDK и LiveKit Agents (голосовой слой) тоже Python-first |
| Слой устройств | Home Assistant | готовые интеграции для тысяч устройств, не пишем свой протокол |
| Мозг Jarvis | Claude API, tool use | инструменты — прямые обёртки над Home Assistant (`set_room_temperature`, `set_room_lights`, `set_room_ac`, `boost_ventilation`, `get_home_status`) |
| Голос (позже) | LiveKit Agents / Vapi / Retell + ElevenLabs (TTS), Piper (офлайн-фолбэк) | не собираем голосовой пайплайн с нуля |
| iPad-приложение (позже) | Apple Business Manager (Custom Apps) + MDM Kiosk Mode | **не** Apple Developer Enterprise Program — против правил Apple для внешних клиентов, риск массового отзыва сертификата |
| Память | отдельное персистентное хранилище предпочтений, накапливается из диалогов | greeting «Иван любит 21°C в кабинете вечером» и т.п. должен переживать рестарт |

## 6. Правила безопасности (жёстко в коде, не только в промпте)

1. Температуру нельзя менять за пределы **16–28°C** без явного подтверждения жильца в диалоге; за пределами **5–35°C** — отказ безусловно, даже с подтверждением.
2. Нет инструмента управления процентом кислорода — это стабильный параметр атмосферы, не ручка. Жалобы на духоту → `boost_ventilation`, и только он.
3. Резкие изменения в нескольких комнатах за один ход диалога → короткое подтверждение у жильца, прежде чем трогать вторую комнату.

Backend спроектирован так, чтобы голосовая платформа или iPad-клиент могли подключиться к нему как к чёрному ящику: `текст/аудио → ответ + действия` (`POST /chat`).

## 8. Definition of Done для текущего MVP (этапы 1–2)

- [x] HA поднимается локально в Docker с mock-сущностями по 4 комнатам, конфиг проходит `check_config` без ошибок.
- [x] Backend держит цикл tool use с Claude API, инструменты — прямые вызовы HA REST API.
- [x] Правило 16–28°C и правило подтверждения нескольких комнат проверены юнит-тестами, а не только описаны в промпте.
- [x] Нет инструмента управления O2.
- [ ] Пройден ручной сквозной тест через реальный `ANTHROPIC_API_KEY` + завершённый onboarding HA (нужны ваши шаги — токен HA и ключ Claude).

## 9. Открытые вопросы (нужно решить отдельно, не блокируют текущий этап)

- Какая именно voice-agent платформа (LiveKit Agents vs Vapi vs Retell) — сравнение по цене/латентности/самостоятельному хостингу ещё не делали.
- Формат хранилища памяти предпочтений: плоский SQLite или что-то с векторным поиском по диалогам — пока не нужно, отложено до этапа 4.
- Как обновлять OEM voice-модули и iPad-прошивку в уже сданных объектах (OTA-стратегия) — вне scope backend-разработки, но важно для эксплуатации.
