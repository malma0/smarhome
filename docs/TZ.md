## 1. Суть продукта

Строим премиальные квартиры/дома под ключ (старт — Новосибирск, дальше Россия, потом мир). На этапе стройки в дом закладывается полный стек умного дома — не только климат и датчики, а вообще всё, что можно автоматизировать: свет, шторы, замки, сигнализация, медиа, бытовая техника, энергетика, участок. Скрытые микрофоны и динамики встроены в потолок/стены, без видимых колонок.

Внутри дома живёт **Jarvis** — ИИ-ассистент:
- с ним можно говорить голосом в любой комнате;
- он управляет буквально всем в доме, что подключено к системе;
- у жильцов есть iPad mini, вмонтированный в стену как пульт — тот же Jarvis, но с экраном.

## 2. Зачем и почему

- **Зачем**: дифференциатор премиум-сегмента жилья. Не «умный дом как набор гаджетов», а цельный ИИ-дворецкий, встроенный в архитектуру дома с самого начала стройки — это нельзя докупить постфактум как колонку с Алисой.
- **Бизнес-модель на старте**: разовые премиум-проекты (стройка + интеграция), не подписка. Экономика — через маржу на самих объектах, не на SaaS.
- **Почему не с нуля**:
  - Голосовое железо — OEM/white-label модули под своим брендом, не разработка чипов/акустики с нуля.
  - Управление устройствами — через Home Assistant, а не собственный протокол опроса датчиков/кондиционеров/замков/медиаплееров.
  - Голосовой пайплайн — поверх готовой agent-платформы (LiveKit Agents / Vapi / Retell), не свой STT/оркестратор.
  - Логика в этих местах — не наше УТП. Наше УТП — то, как это всё интегрировано в стройку и как ведёт себя ассистент.

## 3. Кто пользователь

- **Жилец** — говорит с Jarvis голосом или через iPad-панель. У Jarvis есть характер (см. раздел 5), который либо выбирается жильцом, либо подстраивается под него сам.
- **Семья в целом** — предпочтения хранятся на уровне и семьи, и отдельных её членов (не только «последняя команда»).
- **Мы (на этапе стройки)** — закладываем железо и разворачиваем backend как часть сдачи объекта.
- **Мы (на этапе разработки, до дома)** — тестируем ядро на собственном компьютере: сначала голосом через десктопное приложение, потом — давая Jarvis реально управлять компьютером, прежде чем подключать физический дом.

## 4. Архитектура

Ключевая идея: **ядро ИИ ничего не знает о конкретных устройствах и не завязано на конкретную LLM**. Оно гоняет цикл tool use (через свой `LLMProvider`-адаптер) над реестром тулов, которые ему подставляют снаружи — сегодня в реестре может быть один тул на домен `light`, завтра туда же добавляется `lock`, и ядро не меняется ни строчкой; так же и смена LLM-провайдера не должна требовать переписывания ядра. Это уже проверено на практике: `llm/claude.py`, `llm/groq.py`, `llm/ollama.py` — три реализации одного интерфейса, `agent.py` не изменился ни разу при добавлении второй и третьей.

```
Жилец (голос / iPad)                                    <- фаза 9-10, дом, пока не реализовано
        │
        ▼
Voice-agent платформа (LiveKit Agents / Vapi / Retell)   <- фаза 9, пока не реализовано
   STT → [ Jarvis backend ] → TTS (ElevenLabs, офлайн-фолбэк Piper)
        │
        ▼                                                <- ЗДЕСЬ МЫ СЕЙЧАС: десктопное
Десктопное голосовое приложение (фаза 1, разработка)         голосовое приложение вместо
   STT/TTS средствами компьютера → [ Jarvis backend ]        реального voice-пайплайна
        │
        ▼
┌─────────────────────────────────────────────────────────────┐
│ Jarvis backend                                                │
│                                                                 │
│  Ядро ИИ (device-agnostic И llm-agnostic, фаза 0) ✅ готово     │
│   ├── цикл tool use через LLMProvider-адаптер                  │
│   │     (llm/claude.py, llm/groq.py, llm/ollama.py)            │
│   ├── характер/персона (butler / warm / adaptive-обучаемая)     │
│   └── память: предпочтения по устройствам + стиль общения      │
│         по каждому resident_id                                 │
│                                                                 │
│  Реестр доменных тулов (растёт по одному домену)               │
│   ├── управление компьютером                (фаза 2)           │
│   ├── control_light, control_switch          (фаза 3)          │
│   ├── control_cover                           (фаза 4)          │
│   ├── control_climate, control_humidifier     (фаза 5)          │
│   ├── control_media_player, control_vacuum    (фаза 6)          │
│   ├── control_energy, control_valve, ...      (фаза 7)          │
│   └── control_lock, arm_alarm, ...            (фаза 8, максимум │
│       safety — по умолчанию только чтение статуса)              │
│                                                                 │
│  Слой внимания — rule-engine на порогах (не LLM)     <- позже   │
└─────────────────────────────────────────────────────────────┘
        │
        ▼
Компьютер (фаза 2) → позже Home Assistant (фаза 3+) → реальные устройства дома
```

Jarvis **не** получает непрерывный поток сырых показаний датчиков. Он либо сам запрашивает снимок состояния через tool use, либо (в будущем) его будит слой внимания, когда порог нарушен.

### Карта доменов

| Категория | Примеры | Домен HA | Фаза |
|---|---|---|---|
| Компьютер (ОС) | открыть приложение, работать с файлами, напечатать текст | — (свой ToolRegistry-домен уровня ОС, не HA) | 2 |
| Свет/розетки | сцены, диммер, цветовая температура, обычные розетки | `light`, `switch`, `scene` | 3 |
| Окна/проёмы | шторы, жалюзи, ставни, гаражные ворота, ворота участка | `cover` | 4 |
| Климат и воздух | температура, увлажнитель/осушитель, очистка воздуха, тёплый пол | `climate`, `humidifier`, `fan` | 5 |
| Медиа и техника | ТВ, многозонный звук, робот-пылесос, водонагреватель | `media_player`, `vacuum`, `water_heater` | 6 |
| Энергетика/вода/участок | счётчики, солнечные панели, зарядка EV, полив, протечки, бассейн | `sensor`, `valve`, `switch` | 7 |
| Безопасность и доступ | замки, сигнализация, камеры, видеодомофон | `lock`, `alarm_control_panel`, `camera`, `binary_sensor` | 8 (максимум safety) |
| Присутствие/контекст | геолокация жильцов, датчики занятости, календарь | `device_tracker`, `binary_sensor`, `calendar` | не назначена |
| Коммуникация | пуш-уведомления, внутренний интерком между комнатами | `notify` + свой слой поверх голоса | не назначена |

Порядок фаз 2→8 — от простого/безопасного к сложному/рискованному: компьютер и `light`/`switch` — банальные, обратимые действия; `lock`/`alarm_control_panel`/`camera` — самый высокий риск, поэтому в конце и с самой жёсткой safety-политикой. Управление компьютером идёт первым, потому что позволяет проверить tool use с реальными последствиями (открылась программа или нет) без единого физического устройства дома.

## 5. Персонализация: характер и память

Это часть ядра ИИ (фаза 0, уже реализовано), не умного дома — работает даже без единого подключённого устройства или домена.

- **Три режима характера**, выбираются жильцом (переключаемо в любой момент):
  1. **Сдержанный дворецкий** — статусная, ироничная подача, как у Старка.
  2. **Тёплый семейный помощник** — заботливая, менее формальная подача, лучше заходит с детьми.
  3. **Адаптивный** — начинает нейтрально, затем подстраивается под темперамент и манеру речи конкретного жильца. Реализовано как эвристика v1 (сигналы формальности/многословности/юмора, экспоненциальное скользящее среднее) — не пресет, реальный обучающийся на диалогах компонент, интерфейс спроектирован так, чтобы позже подменить эвристику на настоящий классификатор без изменений в `agent.py`.
- **Память** (SQLite, реализовано) хранит не только предпочтения по устройствам («Иван любит 21°C в кабинете вечером» — появится с фазой 5), но и стиль общения для адаптивного режима — по каждому члену семьи отдельно, уже сейчас.
- **Идентификация говорящего**: пока нет голосового пайплайна с распознаванием говорящего, backend принимает явный `resident_id` рядом с `session_id` — заглушка, которую голосовой слой позже заполнит реальным результатом speaker ID без изменений в остальной логике.
- **Проактивность слоя внимания настраивается жильцом**, а не зашита константой: уровень (например, тихий/сбалансированный/разговорчивый — конкретные градации проектируются вместе со слоем внимания) хранится в том же settings-хранилище, что и характер, на уровне дома. До появления iPad-приложения (фаза 10) значение меняется напрямую через backend-настройки (`GET/PUT /settings`, уже реализовано); в приложении это просто UI поверх того же поля. MVP слоя внимания стартует с консервативного значения по умолчанию (только безопасность/критичное), чтобы не быть навязчивым, пока жилец явно не увеличил уровень.

## 6. Принятые технические решения (не пересматривать без явной причины)

| Решение | Что | Почему |
|---|---|---|
| Язык backend | Python | HA написан на Python — вся экосистема интеграций под него; Anthropic SDK и LiveKit Agents (голосовой слой) тоже Python-first |
| Слой устройств (дом) | Home Assistant | готовые интеграции для тысяч устройств любого домена — не пишем свой протокол ни для датчиков, ни для замков, ни для медиаплееров |
| Мозг Jarvis | LLM за своим адаптером (`LLMProvider`), не прямой вызов SDK по коду | ядро device-agnostic И llm-agnostic; **реализовано и проверено на практике**: `llm/claude.py` (платный, лучшее качество tool use), `llm/groq.py` (бесплатный тариф без карты, открытые модели — **сейчас активен для разработки**, чтобы не тратить деньги на этапе проектирования), `llm/ollama.py` (self-hosted на CPU, только proof-of-concept — ощутимо менее надёжен на tool use). Финальный выбор для продукта — открытый пункт (раздел 9) |
| Голосовой ввод для разработки | Десктопное приложение на компьютере (фаза 1), не браузер и не настоящий voice-пайплайн | нужно разговаривать с Jarvis уже сейчас, до дома и до голосового железа; браузерный демо (Web Speech API) не работает в Firefox и вообще не то, что должно постоянно жить на компьютере |
| Общие вопросы (не про дом) | Jarvis отвечает как полноценный ассистент (как Алиса/Алекса) — общие знания модели + погода через HA `weather` | пользователь явно попросил не ограничивать Jarvis только командами дому; живые внешние данные (новости/курсы/спорт) вне HA — открытый пункт, см. раздел 9 |
| Safety-политика | per-domain, в коде дispatch-а, не только в промпте | у `light` и `lock` принципиально разный уровень риска — единая политика на все домены не годится |
| Голос (дом, финально) | LiveKit Agents / Vapi / Retell + ElevenLabs (TTS), Piper (офлайн-фолбэк) | не собираем голосовой пайплайн с нуля; отдельно от десктопного voice-приложения для разработки |
| iPad-приложение (позже) | Apple Business Manager (Custom Apps) + MDM Kiosk Mode | **не** Apple Developer Enterprise Program — против правил Apple для внешних клиентов, риск массового отзыва сертификата |
| Память | персистентное хранилище (SQLite), часть ядра ИИ (фаза 0) — **реализовано** | нужна уже для характера/персонализации, а не только для предпочтений по устройствам |
| Дообучение (fine-tuning) модели | Не сейчас — не на чем: нужны реальные логи диалогов/команд, которых пока 0 | обучение модели с нуля нереалистично физически (compute/данные/деньги), но дообучение готовой открытой модели под свои сценарии — реалистичный будущий шаг, когда накопятся данные использования |

## 7. Правила безопасности (жёстко в коде, не только в промпте)

Общие для всех доменов:
1. Любое физическое действие идёт через generic-тул своего домена, к которому привязана своя safety-политика — единого «пропусти всё» тула нет.
2. Резкие изменения в нескольких комнатах/объектах за один ход диалога → короткое подтверждение у жильца, прежде чем трогать второй.

Специфичные для доменов, уже реализованных или спроектированных:
- **Климат**: нельзя менять температуру за пределы **16–28°C** без явного подтверждения жильца; за пределами **5–35°C** — отказ безусловно, даже с подтверждением.
- **Вентиляция**: нет инструмента управления процентом кислорода — это стабильный параметр атмосферы, не ручка. Жалобы на духоту → `boost_ventilation`/`control_fan`, и только так.
- **Безопасность/доступ** (фаза 8, ещё не реализовано, принцип зафиксирован заранее): по умолчанию Jarvis только читает статус замков/сигнализации/датчиков. Открыть замок или снять с охраны — всегда явное подтверждение, без исключений и без права «запомнить и не спрашивать в следующий раз».
- **Камеры**: Jarvis не получает видео/фото с камер вообще — только события от датчиков движения («обнаружено движение»). Это решение по приватности, не техническое ограничение.
- **Микрофоны**: аудио передаётся дальше локального wake-word движка OEM-модуля только после произнесённого имени — до этого момента ничего не стримится и не анализируется облаком. Слой внимания работает исключительно по телеметрии Home Assistant (датчики), а не по аудио — то есть проактивность **никогда** не требует фонового прослушивания разговоров.
- **Управление компьютером** (фаза 2, принцип зафиксирован заранее): разрушительные действия (удаление файлов, установка/удаление программ, системные настройки) требуют явного подтверждения жильца, как и multi-target изменения в других доменах — тот же принцип, что и для дома, просто раньше по времени реализации.

- `LLMProvider`-адаптер с тремя работающими реализациями, переключаемыми одной переменной окружения; проверено вживую (не только моками) на всех трёх — Groq оказался заметно надёжнее на tool use, чем локальная модель через Ollama на CPU.
- Device-agnostic `ToolRegistry`, персона (3 режима), память (SQLite) — всё готово принимать первые домены.
- Браузерный voice-демо (`GET /voice`, Web Speech API) собран как быстрая проверка "мозг + голос" — не работает в Firefox, заменён десктопным приложением (фаза 1), это была временная мера.
- Фаза 1 (`voice_app.py`) сделана: STT через Whisper (Groq, бесплатно), TTS — сменный `TTSProvider` (`edge`/`piper`/`sapi`/`elevenlabs`, подробности и честные оговорки по каждому — в README).
- Фаза 2 начата: `open_application` (`app/domains/computer.py`) — первый доменный тул, allowlist без доступа к shell, проверен вживую на реальной LLM (открывает калькулятор по голосу/тексту, отказывается открывать терминал).

Старый climate-прототип (см. историю репозитория) реализует цикл tool use и климат-контроль по 4 захардкоженным комнатам, минуя generic-реестр доменов — рабочий, но архитектурно устаревший (сделан до ядра). Наработки (`ha_client.py`, паттерн `TurnContext`) переиспользуются, когда дойдём до фазы 5 (`climate`).

## 9. Решённые и открытые вопросы

Большинство вопросов закрыты — либо решением, либо осознанной отсрочкой с понятным триггером. Остался один по-настоящему открытый пункт (ниже отдельно).

| Вопрос | Решение |
|---|---|
| Приватность и всегда-слушающие микрофоны | Закрыто. Аудио идёт дальше локального wake-word движка только после имени; слой внимания работает по телеметрии HA, не по аудио. См. раздел 7. |
| Степень проактивности слоя внимания | Закрыто. Настраивается жильцом (settings-хранилище), MVP стартует с консервативного значения по умолчанию. См. раздел 5. |
| Формат хранилища памяти | Закрыто. Плоский SQLite; пересматривается только если реально упрёмся в масштаб (не ожидается для одного дома). |
| Нужен ли Jarvis веб-поиск для live-данных (новости/курсы/спорт) вне HA | Закрыто: да, нужен. Реализация (свой тул поверх стороннего поискового API) пока не сделана — не блокирует текущие фазы. Погода закрывается отдельно, через штатный домен HA `weather`. |

### Открытый вопрос: какая LLM в итоге под капотом продукта

Изначально в брифе — Claude API без вариантов. Причина пересмотра: продукт должен продаваться, но параллельно служит портфолио под трудоустройство в разработку ИИ, плюс на этапе проектирования не хочется тратить деньги — а конкурентоспособную модель с нуля в одиночку не поднять, так что ценность портфолио должна идти не из "своей LLM", а из архитектуры вокруг неё.

Текущее состояние: ядро **llm-agnostic** и это уже проверено практикой — три реализации (`llm/claude.py`, `llm/groq.py`, `llm/ollama.py`) работают через один и тот же интерфейс без единого изменения в `agent.py`. На время разработки активен **Groq** (бесплатно, без карты, открытые модели, заметно надёжнее на tool use, чем локальный Ollama). Финальный выбор модели для продукта в реальных домах — по-прежнему открыт, решается при появлении конкретной причины (стоимость на масштабе, доступ/оплата из РФ, требования конкретного клиента, зрелость open-source альтернативы под tool use, готовность собственного дообученного варианта). Смена провайдера не должна требовать переписывания ядра — это и есть проверка того, что адаптер сделан правильно.

Отдельно от выбора модели: **адаптивная персона** (раздел 5, пункт 3) — вот тот компонент, который проектируется и обучается нами, независимо от того, какая LLM в итоге выбрана под капотом основного диалога. Это и есть "свой ИИ" для портфолио, спроектированный так, что он не выбрасывается при смене провайдера.
